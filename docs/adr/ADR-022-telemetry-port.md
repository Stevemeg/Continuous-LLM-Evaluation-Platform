# ADR-022 — The telemetry port, optional backends, and the adapter-excluded build

| Field | Value |
|---|---|
| Status | **Accepted** |
| Milestone | M13.1 |
| Phase | Phase 13 — Production observability, SLOs, cost/latency telemetry |
| Canonical basis | §14, §19 |
| Requirements | `REQ-N-OBS-1`, `REQ-N-OBS-2`, `REQ-N-OBS-3`, `REQ-N-OBS-4` |
| Constrained by | [ADR-009](ADR-009-observability-core.md) rules 1–6 |
| Implements | [`../architecture/observability-strategy.md`](../architecture/observability-strategy.md) §2, §3 |

## Context

ADR-009 is accepted and this ADR does not revisit it. ADR-009 decided *that* the
core emits telemetry through a vendor-neutral standard, *that* vendor
integrations sit behind a port, and *that* a build excluding every vendor adapter
must pass the full validation suite. It did not decide what the port is, what
"excluding every vendor adapter" means as a build configuration, or how bounded
cardinality is enforced rather than intended. Phase 13 cannot instrument
anything without answering those three, and answering them inside an
implementation commit would be exactly the silent architectural decision the
governance model exists to prevent.

The state being instrumented is empty, which is the one piece of good news:
`src/clep` contains no `logging` import, no metrics client and no tracing
library. Nothing has to be unpicked. What exists instead is a **false
correlation**: three separate columns named `correlation_id` carrying three
unrelated things — `run.correlation_id` set from a caller-supplied header,
`evaluator_invocation.correlation_id` set to `f"{sample_id}:{key}"`, and
`artifact.correlation_id` — and an `x-correlation-id` request header read in
exactly one place, the HTTP error handler. `REQ-N-OBS-1` asks for *one*
identifier recoverable across seven hops. There are currently three identifiers
and no propagation.

The failure mode to design against is the one ADR-020 rule 6 designed against,
in a different costume. Not a wrong metric label: a **forgotten** one. An
identifier put on a metric because it was convenient at the call site, in a code
path nobody reads again, which is invisible until a backend falls over or a bill
arrives. `REQ-N-OBS-4` is unusual among the requirements in that violating it
costs money continuously and breaks nothing immediately.

## Decision

1. **The core depends on no telemetry package.** Instrumentation is expressed
   against a project-owned port, `clep.telemetry`. No domain module, and no core
   container, imports OpenTelemetry, a Prometheus client, or any vendor SDK.
   `REQ-N-OBS-3` is thereby a property of the dependency graph, checkable by
   reading `pyproject.toml` and the import graph, rather than a claim about
   intent.

2. **Every telemetry dependency is an optional extra**, never a runtime
   dependency. The adapter-excluded build of ADR-009 rule 3 is therefore not a
   special build at all: it is `pip install .`, the default. The build that has
   telemetry is the one that asked for it. This inverts the usual arrangement
   deliberately — if the neutral path were the extra, the default build would be
   the one nobody validates.

3. **The default backend is a no-op recorder, and its absence is never an
   error.** A backend that is not installed, not configured, or fails to start
   degrades to the no-op recorder at composition time. A missing telemetry
   backend must never produce an `ImportError` at request time, and must never
   change a verdict. Telemetry that can fail a run is a platform failure the
   product manufactured for itself.

4. **Correlation identifiers are produced by the port's core, never by a
   backend** — ADR-009 rule 4, restated as an implementation constraint because
   it is the rule an adapter is most likely to quietly take over. The identifier
   is opaque, carries no tenant identity, and is generated by the platform even
   when a caller supplies one, with any caller-supplied value recorded as a
   separate inbound reference rather than adopted as the platform's own.

5. **A metric declares its label names and each label's permitted value set
   before it can be recorded, and recording an undeclared label or an
   out-of-enumeration value raises.** This is the load-bearing rule. Cardinality
   is not a convention observed at call sites and checked in review; it is a
   refusal at the point of emission. Tenant, project, run, sample, candidate and
   correlation identifiers are trace and log dimensions and are not expressible
   as metric labels, because the enumeration a metric would have to declare for
   them does not exist.

6. **OpenTelemetry is the neutral standard, not a vendor.** An OTLP exporter
   backend is the reference implementation of the port and satisfies canonical
   §14's "vendor-neutral standard". A backend for a proprietary platform is a
   *vendor adapter* in ADR-009 rule 2's sense and additionally requires the
   licence review of ADR-009 rule 6 before adoption.

7. **Backends are selected at composition time from configuration**, alongside
   every other injected dependency, and never imported at module scope in domain
   code. The application that has no telemetry configured constructs the no-op
   recorder and never loads an adapter module at all.

## Rationale

Rule 5 is why this ADR exists; the rest is bookkeeping around it.

`REQ-N-OBS-4` says label cardinality shall be bounded. Every project that has
ever violated that requirement had a developer who knew the rule. The rule is
easy to state, easy to agree with, and violated by one plausible line of code in
a diff nobody flags — because adding `run_id` to a metric is *locally* the most
helpful thing to do, and its cost appears somewhere else entirely, later, as
money. A rule enforced by discipline at every call site is a rule that survives
until the first busy week.

So the port refuses. A metric that has not declared a label cannot carry it, and
a label that has not declared its values cannot take one. There is no enumeration
of run identifiers to declare, so putting a run identifier on a metric is not a
policy violation to be caught in review — it is a call that raises. That is the
same shape as ADR-020 rule 6: the defence is not a check that must be remembered
but a default that is "does not work".

Rule 2 inverts the conventional packaging because of what ADR-009 rule 3
actually demands. If telemetry were a runtime dependency and its exclusion a
special configuration, then the *validated* build would be the instrumented one
and the excluded build would be an occasional exercise — which is how a
"vendor-neutral core" becomes true only on the day somebody tests it. Making the
neutral build the default means every test run, every developer's machine and
every CI invocation exercises it, and the instrumented build is the one carrying
the burden of proof.

Rule 3 exists because of what this platform is for. `REQ-X-10` requires platform
failure to be distinguishable from quality failure. A telemetry exporter that
raises on a full queue, and takes a gate evaluation down with it, converts an
observability problem into a verdict — the precise confusion the product exists
to prevent. Telemetry observes; it does not participate.

Rule 4's "recorded as a separate inbound reference rather than adopted" matters
more than it looks. A caller-supplied `x-correlation-id` is untrusted input: it
can collide with another tenant's identifier by accident or on purpose, and an
identifier a tenant controls is one a tenant can use to make two runs look like
one. Keeping the caller's value as a recorded reference preserves the client's
ability to join its own logs to ours without letting it choose our identity.

## Consequences

- Every metric acquires a declaration, and adding a metric becomes two steps.
  This is the intended cost of rule 5, and it is the same trade ADR-020 rule 6
  made.
- Two dependency configurations must be tested: the default, and the default plus
  telemetry extras. The default is tested by every existing test run; the second
  is the addition.
- Correlation identifier propagation crosses every container boundary, including
  into the evaluator sandbox — where it must not widen the grant ADR-006 rule 3
  establishes. The identifier is carried as data, not as a capability.
- The three existing `correlation_id` columns are not all alike, and inspection
  before instrumenting found that out:
  - `run.correlation_id` is declared, nullable, and **never written by anything**.
    `create_run` accepts the parameter and no caller supplies it, so the
    contract's `correlationId` field has always been absent from every response.
    Phase 13 populates it with the platform correlation identifier. That is the
    column finally doing what it was declared for, not a repurposing.
  - `evaluator_invocation.correlation_id` is `NOT NULL` and currently written as
    `f"{sample_id}:{key}"` — a value **fully derivable from `run_sample_id` and
    `evaluator_version_id` in the same row**, so it carries no information the
    row does not already hold. It is written with the platform correlation
    identifier instead. Nothing is lost, and a column named `correlation_id`
    starts holding a correlation identifier.
  - `artifact.correlation_id` is `NOT NULL` and is the artifact hop of the chain
    already; it receives the platform identifier at its writers.
- The chain is recoverable by one query keyed on the identifier. Hops reachable
  from the run by foreign key — samples, costs, judge records — are recovered by
  join rather than by denormalising the identifier onto every table, because a
  copied identifier is a second thing that can disagree with the first.

## Deferred

- **Trace sampling policy.** Meaningful only against production traffic volumes
  that do not exist. The port takes a sampler; the deployment chooses one
  (Phase 14).
- **Dashboards and their storage.** Canonical §14 names Grafana "where
  appropriate"; a dashboard is a deployment artifact, not a platform capability.
- **Adoption of any proprietary vendor adapter**, which ADR-009 rule 6 gates on
  licence review and which no requirement asks for.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Import the OpenTelemetry API directly in domain code, treating it as the neutral standard | It is the neutral standard, and it is still a dependency. `REQ-N-OBS-3` is verified by a build that excludes telemetry entirely; if the API is imported at module scope, that build does not import. The port costs one indirection and makes the requirement testable. |
| Enforce cardinality by review, or by a validator that greps for identifier names in metric calls | Substring inspection of call sites is the check this project has lost nine checks to. It cannot see a label built from a variable, and it passes the moment somebody writes `labels=d`. |
| Enforce cardinality only in the backend adapter | Puts the rule outside the core, contradicting ADR-009 rule 5, and makes it absent precisely in the default build that has no adapter. |
| Make telemetry a runtime dependency with an "off" switch | The switch is a configuration flag governing whether an observability requirement is met, which is the shape `REQ-F-12-8` forbids elsewhere; and it leaves the adapter-excluded build untested by default. |
| Adopt the caller's `x-correlation-id` as the platform identifier when present | Lets a tenant choose an identifier the platform indexes, joins on, and reports from. Collision becomes a tenant-controllable event. |
